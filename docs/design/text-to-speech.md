# Listening (Text-to-Speech & Recording)

← [Design Docs](README.md)

One capability — **listen to your book** — over a shared segmentation + position
foundation, in two playback modes:

- **Live read-aloud** — synthesize on the fly with an on-device engine.
  Instant, plays offline once a voice is downloaded, follows the text with a highlight and
  page-turns, and has a full player (transport, scrubber, per-sentence highlight/note/bookmark).
- **Recorded audio (pre-generated)** — record a book (or chapters) once with a
  higher-quality source (on-device Piper or a Kokoro/OpenAI-compatible server), cache it on
  device as MP3s, and play it back fully offline with the listening position synced to the
  reading position. Multiple **editions** (one voice each) and **mixes** (a per-chapter blend of
  recorded and live voices) can coexist; you choose which plays from the reader.

The audio *source* (a system voice, on-device Piper, a local Kokoro server, a cloud voice) is
an engine detail; both modes ride the same sentence segmentation, CFI position-map, and
highlight/scroll machinery.

Both modes run on **desktop, iPad, and Android**. Two *live* engines ship: **Web Speech** (system
voices, desktop/iOS) and **Piper** (on-device neural, everywhere including Android). Recorded audio
is generated by **on-device Piper** or a **Kokoro/OpenAI-compatible server** and played back from
cached MP3s. There is no **eSpeak/meSpeak** engine: its ~1.8 MB asm.js would dominate the bundle,
and it sounds robotic. The live voice is chosen in Settings → **Listening**; recordings + mixes are
managed from the reader's **Voice & source** popup and the **Manage recordings** dialog. The unified
live-vs-recorded playback is transparent — the player prefers a recording when one exists for the
current chapter and falls back to the live voice otherwise.

## Architecture at a glance

```
TtsController (src/reader/TtsController.ts)   ← owns the bar, the full-screen player,
  │                                              the play loop, highlight/page-follow,
  │                                              bookmarks, wake lock, control lock
  ├─ TtsEngine (src/reader/tts/TtsEngine.ts)  ← speak/pause/resume/stop/setRate
  │   ├─ WebSpeechEngine   (system voices; desktop + iOS)
  │   └─ PiperEngine       (on-device neural; all platforms incl. Android)
  │        └─ piper-worker.ts  ← phonemize + ONNX inference off the main thread
  ├─ tts-blocks.ts         ← sentence segmentation → ReadingUnit[] (text + CFI + block)
  ├─ pacing.ts             ← inter-clip + structure-aware pauses
  ├─ voice-catalog.ts      ← the curated "Orbis voices" catalog
  ├─ voice-picker.ts       ← shared VoicePicker UI (list/filter/download/preview/speaker)
  ├─ live-voice-picker.ts  ← device live-voice binding for VoicePicker (Settings + in-reader)
  ├─ recording.ts          ← recording pipeline (Piper / Kokoro → MP3 + manifest)
  └─ recording-editions.ts ← editions.json + per-edition manifests + mix pointer manifests

Reader-side dialogs (opened from the bar / player):
  VoiceRecordingsModal   ← "Voice & source" popup (voice provenance + recording picker)
  RecordingsModal  ← "Manage recordings" (record editions, build mixes, view/delete)
```

`TtsController` is a reader collaborator wired through `ReaderContext` + `TtsHost` (see
[reader-architecture.md](reader-architecture.md)). It never pierces foliate's closed shadow
DOM — text comes from the rendered/parsed section document, and highlights ride the existing
annotation-overlay path.

## Shared foundation

### Sentence segmentation (`src/reader/tts/tts-blocks.ts`)

The book is read as **sentence units** (`ReadingUnit`) with **text-node ranges** (not
element-boundary ranges), because text-node ranges draw reliably on the annotation overlay and
let the view page along *within* a long paragraph. Each unit also carries its enclosing
**block** (paragraph) range, used for "highlight the whole paragraph" and for structure-aware
pauses.

Pipeline: `getBlocks(doc)` (paragraph structure) → `collectRangeTextNodes` (text nodes within a
block, descending through inline markup — ported from foliate `text-walker.js`, driven by the
epub `doc` since foliate's own version uses the global `document`) →
`Intl.Segmenter({granularity:'sentence'})` with foliate's offset→node mapping to build a `Range`
per sentence. `getReadingUnits(doc, maxChars)` optionally groups consecutive sentences into
chunks up to `maxChars` (the **Read ahead** setting) — chunks only ever break at sentence
boundaries.

**A unit needs at least one letter or digit** (`SPEAKABLE`, `\p{L}\p{N}`). A block of pure punctuation is a real
thing in a real book — `](` left by a malformed markdown link, a lone `)`, an em dash on its own line — and
without the rule each one would be a reading unit: a whole synthesis request in a recorded run, and a stop the
highlight sits on in live listening. Not `\w`, which is ASCII-only and would throw away 日本語 and Ελληνικά
wholesale; a number, a currency amount and a CJK sentence all qualify. Note this only affects punctuation that is
*its own unit* — the Unicode sentence-break algorithm keeps trailing punctuation attached to the sentence before
it, so `?!` mid-paragraph is never a unit of its own.

Three gotchas:

- **Newlines are sentence boundaries** (UAX-29). Pretty-printed epub HTML wraps text with hard
  newlines, splitting sentences at every source line. Fix (mirrors foliate): replace newlines
  with spaces **length-preservingly** (`\r\n` → two spaces) so offsets still map.
- **Sentences spanning inline markup** (`<i>`, footnote refs) need the full node set; a
  hand-rolled `intersectsNode` collection drops interior nodes and truncates sentences.
- **A range that leaks out of its block paints nothing, silently.** A block's last sentence has no
  sentence boundary after it, so the segment runs on and swallows the whitespace between `</h1>`
  (or `</li>`) and the next block — putting the range's `commonAncestorContainer` on `<body>`.
  `Overlayer.add` then hands it to foliate's `#splitRangeByParagraph`, which draws a range as-is
  only when there is **no** `<p>` under the cAC; otherwise it draws only the parts clipped to
  *intersecting* `<p>`s, and a leaked range intersects none of them — empty rect list, empty `<g>`,
  no highlight, no error. A leaked `<p>` range still intersects its own `<p>` and gets clipped
  back into shape, so it is headings and list items that lose the reading highlight. Fix: `tightSpan` for block ranges, and mapping each sentence's
  **trimmed** bounds, so a unit range never leaves its block. (`tightenRange` in `range-utils.ts`
  repairs the identical leak for stored annotation CFIs — the "phantom search result" — after the
  fact; here the offsets are already known, so the loose range is never built.) Guarded by
  `tts-units.test.ts`, which reproduces foliate's clipping rule and asserts every unit paints.

`normalizeForSpeech()` also rewrites heading Roman numerals ("Chapter I" → "Chapter 1"),
title-cases ALL-CAPS **words** so espeak doesn't spell them out, and collapses a **URL in the
text** to `web link <host>` ("web link x dot com") — dots spelled out, path/query/port/userinfo and
`www.` dropped, `mailto:` and bare addresses read as `email link <host>`. Matched narrowly: a
scheme, a `www.` prefix, or a host **with a path**; a bare `x.com` is left alone, since
abbreviations and prose false-positive more often than they help. Only URLs that are *visible text*
are affected — an `href` is never spoken, so a link whose text is prose reads as written.
Punctuation around the URL is put back after the reading, so a sentence-final period still reaches
the engine. It takes an optional compiled **pronunciation glossary**, applied last — see "Speaking
a selection, and the pronunciation glossary" below. Every synthesis path funnels through this
function, which is why one glossary entry reaches live voices and both recording engines alike
(and why prepared MP3s recorded before a rule changes keep the old reading until re-recorded).

**ALL-CAPS: word or initialism?** Title-casing is right for a caps *word* (`CHAPTER` → "Chapter")
and wrong for an *initialism*, which the engine spells correctly when left in caps — title-casing
would turn `RIAA` into "Riaa" ("ree-ah"). `isInitialism()` tells them apart on spelling shape: no vowel at
all (`HTML`), vowels only in the first/last position (`AWS`, `USA`, `FBI`), or a run of 3+ vowels in
a short token (`RIAA`, `IEEE`). Those are left in caps; everything else is title-cased, including
three-letter words (`FUD` → "Fud"). A possessive or plural is held aside during the test and put
back after, so the apostrophe never counts toward the token's shape (`AWS's` does not become
"Aws's"). Roman-numeral tokens are exempt whatever their shape, since the
rule below owns them.

The test is a heuristic and cannot be anything else: **convention**, not spelling, decides that AWS
is spelled and FUD is said, and both are equally pronounceable. Known costs: `MIT` and `CIA` read as
words, `QUEUE` reads as letters, and three-letter words whose vowels sit only at the edges (`ONE`,
`TWO`, `THE`) read as letters — fixing that group would need a word list. The pronunciation glossary is the per-book fix for
an acronym that matters.

`getWordUnits(range)` segments **one sentence into word units** for the word-granularity reading
highlight (`Intl.Segmenter({granularity:'word'})`, word-like segments only so the highlight never
lands on a space or a bare comma). It is computed lazily per sentence, so the other highlight modes
never pay for it. It needs its own text-node collection (`rangeTextSlices`) rather than
`collectRangeTextNodes`: a *sentence* range starts and ends mid-node, and
`collectRangeTextNodes`'s `comparePoint(node, 0)` test reports -1 for a start container the range
enters partway through — which would drop the first word of every sentence but the first. Slices
are kept on *intersection* instead, preserving both partial edge nodes and all interior ones.

`cumCharBounds(units)` + `unitIndexAtFraction(cumChars, count, frac, from)` are the shared
char-proportional position estimate — used for sentences within a synthesis chunk and for words
within a sentence. Exact when the engine reports a real character index (Web Speech
`onboundary`); an estimate when it reports elapsed time (Piper, recorded MP3).

### Position map & sync (CFI)

Every unit maps to a **CFI**, so a sentence's audio and its place in the text are two views of
one position. That's what makes highlight-follow and the read↔listen handoff for recordings
work. Highlights use `addAnnotation({value: cfi, color})` (drawn by
the overlay's dedicated reading-highlight key so it never clobbers user annotations) +
`renderer.scrollToAnchor(range)` to page to it.

## Engines (audio sources)

An engine only speaks a chunk of text and reports when done; segmentation, highlighting, and
navigation are the controller's job — so engines are cheap to add. `TtsEngine`:
`isAvailable()`, `speak(text, startFraction?, pauseAfterMs?)`, `pause()`/`resume()`, `stop()`,
`setRate()`, `canPauseMidUtterance()`, optional `prime()` (prefetch).

### Live engines

- **`WebSpeechEngine`** — `speechSynthesis` + system voices. Desktop (Electron) and iOS/iPadOS
  (WKWebView); **absent on Android's WebView**. True mid-utterance pause/resume. iOS/iPadOS only
  expose ~6 compact voices (no Siri/Enhanced) — so Orbis voices are the better path there.
- **`PiperEngine`** — on-device neural (VITS via onnxruntime-web WASM + an espeak-ng
  phonemizer), running entirely in the WebView. Works **everywhere, including Android**, which
  otherwise has no live engine. Playback is Web Audio (decode PCM into an `AudioBuffer`, play
  via `AudioBufferSourceNode` — instant `start()`, no per-sentence startup gap). See the
  constraints below.

### Piper on-device — constraints

- **Asset delivery bypasses the WebView CSP.** The phonemizer `.wasm`/`.data` are injected as
  in-memory bytes (Emscripten `wasmBinary`/`getPreloadedPackage`, never `fetch`/`fs`); ORT's
  wasm + the voice model are fetched via Obsidian's `requestUrl` (CSP-exempt; ruby.wasm
  precedent). Only ~600 KB of ORT/phonemizer glue ships in `main.js`; everything else downloads
  once at runtime and is cached to disk under `<configDir>/plugins/orbis-reader/piper-cache/`
  (so later sessions load instantly and fully offline). A fatal load failure stops playback with
  a notice rather than silently skipping.
- **Model download is ranged/chunked on mobile.** Mobile `requestUrl` returns the body
  base64-encoded (~1.37× inflation); buffering a whole model at once OOM-crashes the Android
  WebView. Pull ~4 MB ranged chunks into a pre-allocated buffer. (Size is not the limit —
  buffering is; Android runs the full model fine.)
- **Medium / 256-symbol voices only.** The 130-symbol "low/x-low" tier crashes ORT (`Gather`
  index out of bounds) on rarer phonemes the newer espeak emits; the catalog is medium-only.
- **Synthesis runs in a Web Worker** (`piper-worker.ts`) — phonemize + ONNX inference (the heavy
  ~1–18 s work) never block the main thread's UI or audio scheduling; the main thread only reads
  the model/wasm bytes (`requestUrl` + vault adapter) and does the Web Audio playback, handing
  bytes to the worker. Inference is still effectively single-threaded, so tier is still bounded
  by real time: **medium** synthesizes in ~0.7–2 s/sentence (hidden behind playback by a 2-ahead
  prefetch buffer), while **high** (4–18 s/sentence) can't keep pace and is unusable for *live*
  playback on any platform (fine for background *generation*).

### Generation sources (feed the recording, see below)

- **HTTP / OpenAI-compatible** (`/v1/audio/speech` via `requestUrl`) — self-hosted **Kokoro**
  (best local quality) or any cloud endpoint by swapping URL + key. Used for generation; not
  wired for live playback.
- **Piper for generation** — the same on-device engine runs any tier (incl. high) as a
  background batch job, giving a fully-offline, free generation source with no server.
- **macOS `say` / Windows SAPI** — desktop-only local generation via Node `child_process`.
  *Not built.*

## Voice selection

Chosen in **Settings → Listening** (`OrbisSettings.buildAudioTab` → `buildVoicePicker`; the tab
key is internally `"Audio"` but shows as **"Listening"**). Three groups:

- **Orbis voices** — a curated catalog of downloadable neural voices (`voice-catalog.ts`; 14
  single-speaker, medium/256-symbol, ~60 MB each). They sound the same on every device and work
  offline once downloaded. Choosing one downloads nothing: the button under the list reads **Download · N MB**
  until it is on the device, then **Preview**.
- **Multi-voice models** — `libritts_r` (US, 904 speakers) and `vctk` (GB, 109 speakers): one
  download exposes many voices, picked by a 1-based number with ‹ ›/Enter preview.
- **System voices** — the OS's Web Speech voices (desktop/iOS), locale-scoped to the UI language
  with the junk "novelty" voices filtered out; empty on Android.

**Per-device preference.** `voicePrefs` is keyed by `deviceId` (`getOrCreateDeviceId`) so a
synced `data.json` still lets each device keep its own voice — a Mac choice never bricks Listen
on Android. Resolution (`resolveDeviceLiveVoice`): an explicit pref wins; with no pref, every device uses the
default Orbis voice, so the first listen offers it rather than quietly making the OS the narrator. A system pref on
a device without Web Speech falls through to Orbis.

**First run** (`FirstVoiceModal`): "Listen needs a voice" — download a recommended Orbis voice,
or fall back to a system voice where available. **Browse voices** opens the Live voice picker over the book
(`openLiveVoicePicker`). On Done
(`browseVoicesThen`), a voice able to speak opens the listening bar, and a voice chosen but still to download
brings the prompt back naming it; otherwise it ends there. **"Able to speak" is read, not inferred from a
choice**: Preview downloads the voice already chosen without changing the choice, so waiting for a change would
leave the bar closed after exactly that.

**One binding, two surfaces.** The device live-voice control (the `[ Orbis | System ]` toggle +
list + speaker stepper, mapped onto `voicePrefs`) is single-sourced in
`live-voice-picker.ts::liveVoicePicker()` — it returns a `VoicePickerHost` + methods bound to
`getDeviceVoicePref`/`setDeviceVoicePref`. Both **Settings → Listening** and the in-reader
**Change voice** popup (`OrbisReaderView.openLiveVoicePicker`) build a `VoicePicker` from it, so
they drive the identical control; the caller supplies `setPref` (which also frees the warm worker
and re-seats any active listening).

### Deleting a voice: one place, and never the live voice

A voice is deleted only from **Settings → Listening → Downloaded voices** (`downloaded-voices-dialog.ts`), which lists
the Orbis models on this device with their sizes. **None of the pickers has a delete.** It used to sit beside
Preview and act on the selected voice — and selecting a voice makes it the live voice, so the one voice it could
reach was the one in use: deleting any other meant choosing it first, and deleting the live one left the device
with nothing to read in.

**The live voice's row is locked** — *Selected live voice*, its trash disabled with the reason in its tooltip — and
nothing else is. "Live" is decided by `resolveDeviceLiveVoice`, the rule that picks the voice that speaks, so the
lock and the voice can't disagree; compared by model file, so a multi-speaker model is in use whichever speaker is
chosen (`downloaded-voices.ts`). On a system voice nothing is locked and every Orbis voice can go; on Android, with no
system voices, one always stays. Every other use asks before downloading again, so it warns at most: the voice for
new recordings adds a line to the confirmation, and a voice a mix names for a track falls back to the live voice
with a notice. A recording in progress is unaffected — it loads its voice once, at the start of the run.

**Voice vetting note.** Some Piper voices garble short inputs (chapter headings) via a
stochastic duration-predictor blow-up; the catalog admits only voices that pass a
samples-per-phoneme check, which excludes john and norman. Mitigations live in `normalizeForSpeech` + the synth
path (title-case ALL-CAPS, zero duration noise for very short inputs).

## The player

Two surfaces, sharing one controller:

- **Compact read-along bar** — a strip that shares the top-overlay slot mutually-exclusively
  with Search / Go To / Display. Transport + progress; the text stays visible and follows along.
  A **voice chip** on the left (`[ 🎤 Heart · Mix 1 ⇔ ]`) shows the voice reading the current
  chapter, whether it was recorded or is being spoken now, and which recording or mix is selected.
  It opens the Voice & source popup — see below. The chip also shows the speed, last (`ChipSpeeds`): always in the
  full player, and on the bar only while the names fit whole, since they say which audio this is. No speed button:
  speed is the popup's SPEED block, so the bar's
  width goes to the transport — 34px circles on a phone, the chip's height, with room around ▶ — and the chip.
- **Full-screen "now playing" player** (`textHidden`) — cover, title/author, position-aware
  chapter label, the same **voice chip** under the label, a draggable chapter progress
  **scrubber** with elapsed/remaining/book-left times (a live track's are word estimates at 155 WPM, pure functions
  in `tts/listen-duration.ts`; the bar's drag and keys are `tts/progress-scrub.ts`), transport (▶/⏸ · ⏮/⏭ chapter · ±15 s skip),
  and four action buttons, configure to capture: the **marks** for listening, **passage**, **note** and
  **bookmark** the sentence being read (sentence- or paragraph-scoped per settings) — the bookmark nearest a right
  thumb. No speed button: the chip shows the speed and opens Voice & source, where it is changed.

Both open without auto-playing (you press ▶). Neither has a text input, sidestepping the
mobile-keyboard black-screen bug class. Opening the full player never moves a playing/paused
position; it only homes to the page when idle.

**Bookmarks** are unified reading + audio bookmarks: a bookmark is a precise **sentence-anchor
CFI** (not just a page), tagged `kind: 'reading' | 'audio'`, differing only by the saved-panel
glyph. Navigating to one **flashes** the anchor (blink via an overlay-key toggle — WAAPI dies on
foliate's `Overlayer.redraw()` after a cross-section jump). An audio bookmark is made from the
player (or the main toolbar while audio is playing/paused). See
[marks-and-notes.md](../guide/marks-and-notes.md).

**Last location.** The sentence being read is persisted as the book's last-read location (the
player doesn't page, so no relocate fires to save it) and flushed on close, so resume lands on
the exact sentence.

---

**Cover art.** The full-screen player shows the book's cover, resolved by
`OrbisReaderView.getCoverBlob()`: live extraction first, then the `coverImage` cached in the book's
`.orbis` file. Books with no cover art get a rendered title + author stand-in instead of a gap. Cover
extraction is deliberately *not* read off `bookResources` — that field is gated on `loadBlob`, which MOBI and
AZW3 don't expose, so reading it there would silently lose the cover for those formats. Full pipeline, including why
the stand-in isn't cached as an image, in [orbis-data-view.md](orbis-data-view.md#cover-art).

## Voice & source (the chip, the popup, and provenance)

The bar/player **voice chip** answers four questions at once and opens the **Voice & source** popup
(`VoiceRecordingsModal`) to change any of them. It reads `[ 🎤 Heart · Mix 1 ⚙ ]` — an origin
glyph, the voice reading the *current chapter* (so for a mix it turns over per chapter), and the
recording or mix selected for the book. Its trailing glyph is a **sliders/options icon**, not a
dropdown caret — it opens a panel, it isn't an inline select. The chip refreshes when the bar
opens, when the chapter changes (piggybacks `updateChapterLabel`, guarded by `chipSection` so a
mere page relocate doesn't re-fetch), and after the source/edition changes
(`reloadForPlaybackChange`, forced).

### Four facts, none derivable from the others

The voice alone would leave a reader listening to "Mix 1" with no way to discover it anywhere but
inside a popup. Adding the selection as a second text slot is **not enough on its own**, because
the selection and what's playing come apart on a half-recorded book. So there are four
fields on `VoiceInfo`, and the chip is two text slots plus a glyph plus a bracket:

| Fact | Field | Carried by |
|---|---|---|
| Which voice | `label` | First text slot |
| Recorded, or spoken now | `recorded` | **The glyph** — mic, or broadcast arcs |
| Which recording/mix is selected | `source` | Second text slot |
| Whether this voice came from it | `fromSelection` | Parentheses round the second slot |

| State | Chip |
|---|---|
| Recorded track, recording renamed | `🎤 Heart · Night reads` |
| Recorded track, recording unnamed | `🎤 Heart` |
| Mix chapter pointing at a recorded source | `🎤 Heart · Mix 1` |
| Mix chapter pinned to a live voice | `((•)) Amy · Mix 1` |
| Coverage gap — this chapter isn't in the selection | `((•)) Amy · (Mix 1)` |
| Always-live on, over a real selection | `((•)) Amy · (Mix 1)` |
| "None — use the live voice", or no recordings at all | `((•)) Amy` |

Three rows carry the reasoning. **Row 4** is why `fromSelection` is not the inverse of `recorded`:
a mix that names a live voice for a chapter is live *and* deliberate, so it takes no parentheses.
**Row 5** is why the second slot isn't simply `idx.active`'s label — you are hearing the device
voice, and `Amy · Heart` would be claiming Amy came from Heart. **Row 2** is the collapse rule: a
recording is *named by its voice* until someone renames it, so its name would repeat the first slot
and `sourceBeside` drops it. That rule is also what makes renaming a recording worth having.

Deciding row 6 this way means `currentVoiceInfo` loads the editions index **even when always-live
is on** — that override is precisely when a reader wonders why the recording they made is silent,
and the answer is that the selection is still there and still being overridden.

### Where a recording's name is used

A recording can be renamed, and the name then appears everywhere it identifies the item — the library row, the
detail header, the chip's second half, and the mix Source dropdown. **The dropdown gives the voice beside it**:
"Night reads (Amy — American English, Female) · recording". Composing a mix is choosing what each chapter will
*sound* like, and the chapter rows it fills in name the voice in full; with the name alone, the reader would have to
remember which voice they had called Night reads. It said the voice alone for a while, and then a reader who had
named a recording looked for that name and couldn't find it. An unnamed recording says its voice once. See
`mixSourceLabel`.

### Nothing selects a recording or mix but the reader

Recording and playback are independent, so what plays changes only when the reader chooses it under **Source**. An
empty `active` in `editions.json` is a choice — **None — use the live voice** — not a gap to fill: a new mix is never
selected, recording another voice leaves the selection alone, and deleting the selected recording or mix selects
None rather than the newest one left. The one exception is a book's **first** recording, selected because there was
nothing to choose before it. A new mix used to fill an empty selection, so with None selected, **Add mix** changed
what played.

The delete confirmation names the item, not a voice: it deletes one recording, and that recording's label need not
be a voice.

### The glyph pair

`reader/tts/voice-glyphs.ts` holds both, and holds them alone: a mic for recorded audio, two arcs
each side for a voice speaking now. **One definition, four surfaces** — the two chips, the popup's
VOICE row, every chapter row of a mix, and the "Always use the live voice" switch — because a
vocabulary only teaches if it is identical everywhere, and four copies of an SVG string would
diverge.

They are drawn, not named through `setIcon`, for a reason worth keeping: **an unknown icon id
renders nothing, silently**, and Obsidian's icon set isn't enumerable from outside the app. Every
other glyph in the player is hand-rolled the same way. The live arcs are `SPEAKER_SVG`'s own arcs
mirrored, cone removed — the house volume glyph with a symmetrical source — so the pair sits beside
the transport without looking imported.

Three decisions inside that file, each judged at the size the glyph is actually seen:
the mic **loses its stand's base bar** (better at 32px, worse at 15, where it thins everything
above it); the live glyph **has no center dot** (two device pixels reads as grit, not as a source);
and the mic **marks state, never an action** — nothing that starts a recording wears it, because a
mic on a control means "tap to speak" everywhere else in software.

The popup's VOICE row is where the pair is explained, and nothing there is labeled a legend: the
glyph sits one line above `reason`, a full sentence saying what it means, at the moment someone
came looking. The chip is glyph-only, so its `aria-label` carries that same sentence in words —
a shape says nothing to a screen reader.

### The two-origin principle

For whatever chapter is playing, the voice has exactly one of two origins, and the UI's shape
tells you which lever changes it:

- **Fixed by the selection** — a recorded chapter, a mix chapter pointing at a recording, or a
  mix chapter pinned to a specific live voice. You change it via the **Recording** block (pick a
  different edition/mix, or Manage recordings).
- **Your device live voice, from options** — no recording covers this chapter, the mix leaves it
  on the default live voice, "always use live voice" is on, or the book has no recordings. Here
  the popup shows a **Change voice** button (opens the shared live-voice picker).

> **The "Change voice" button appears only in the second case** — so pressing it is *guaranteed*
> to change what you're hearing now. No button that silently does nothing.

`OrbisReaderView.currentVoiceInfo(chapterIndex)` returns `{ label, fromDeviceLive, reason }` (see
`VoiceInfo` in `TtsHost.ts`); the chip uses `.label`, the popup uses all three. The described
chapter is `TtsController.describedChapterIndex()` — the chapter being read when playing/paused,
else the one the page the reader is parked on sits in. Reason lines:

| Current voice origin | `fromDeviceLive` | Reason line |
|---|---|---|
| Recorded chapter / mix recorded source / mix-pinned live voice | `false` | "From your recording selection." |
| Partial coverage — chapter not recorded | `true` | "Your live voice — this chapter has no recording." |
| Mix chapter on the default live voice | `true` | "Your live voice — this chapter uses the default." |
| "Always use live voice" override on | `true` | "Your live voice — always-live is on." |
| No recordings for this book | `true` | "Your live voice." |

The popup's **SOURCE** block is the recording/mix dropdown (whenever ≥1 recording exists) or a
"no recordings" line, plus a coverage line when the active recording is partial, plus **Manage
recordings and mixes**. The dropdown always offers **"None — use the live voice"** as its first item: a
**per-book** choice that clears this book's `active` edition (`clearActiveEdition` → `active =
null`), so the whole book reads with the device live voice even though recordings exist. Playback
resolves a null `active` to the live engine per chapter, so this adds no playback code; it's
distinct from the global "always use live voice" Settings toggle (which forces live for *every*
book). A small link opens the full Settings tab (the live voice + always-live override live there).

The **SPEED** block, under VOICE, is the speed control (`TtsController.buildSpeedControl`) — the only place speed is
changed: a slider, a number field and **×**, bound as the Display menu's Line spacing is
(`bindRealTimeSliderInput`), applied as either moves, and clamped to 0.5–3 when the field is left.

## Recordings: editions & mixes

Recordings live under the book's audio dir (`!orbis-data/audio/<book>.audio/`, see `audioFolderName`) as **editions**:

```
editions.json            → { version, active, editions: EditionMeta[] }   (active = what plays)
<editionKey>/manifest.json + chXXXX.mp3                                   (one voice per edition)
<mixKey>/mix.json        → { version, chapters: MixChapter[] }            (pointers, NO audio)
```

- **Edition** = a full-or-partial recording in **one voice**. `EditionMeta{ key, engine, model,
  voice, createdAt, kind?: 'voice' | 'mix', label? }`; `editionKey(engine, model, voice)` slugs a
  stable folder name. **Recording target and playback `active` are independent** — recording a new
  voice never hijacks what's currently playing.
- **Mix** (`kind: 'mix'`) = a per-chapter blend that **stores no audio of its own** — `mix.json`
  is a pointer manifest, so a shared MP3 is never duplicated. Each `MixChapter` points at *either*
  a recorded source edition (`sourceKey`, gated to chapters that source actually recorded) *or* a
  live voice (`live: MixLiveVoice`, assignable to any chapter). `MixLiveVoice` is
  `{kind:'orbis',voiceId} | {kind:'system',voiceURI} | {kind:'default'}`; **default is dynamic** —
  it follows the device's current live voice at playback, not a snapshot. Building/assigning is
  done in `RecordingsModal` (select chapters → choose a recorded or live source → assign);
  `pruneEmptyEditions` skips mixes (they have no manifest) and `pruneMixPointers` drops only
  recorded pointers whose source lost the chapter (live pointers always survive).

**Playback resolution.** `loadEditionChapter(key, index)` resolves a mix chapter's audio +
segments from its *source* edition, while `chapterCount`/`laterDuration` span the whole mix. A
mix chapter with no recorded pointer (live, or a lost source) returns `null` → the controller
reads it with the **live engine**.

**Per-chapter live voice override.** A mix chapter pinned to a *specific* live voice needs the
live engine to use that voice, not the device pref. The controller holds a `liveOverride`
(`LiveVoiceOverride`) recomputed **once per section** at the single choke point in `speakUnit`
(cached by `overrideSection`); `resolveSource` / `makeEngine` / `resolvedVoiceKey` consult it, so
non-mix playback is unaffected (override stays null). Recorded-then-live transitions:
`advanceToNextSection` loads recorded audio for the next chapter and hands off to the recorded
player when present, else continues live.

## Pacing (`src/reader/tts/pacing.ts`)

The gap after each spoken unit is **jittered** around a base (~275 ± 50 ms) so it isn't
metronomic, and **structure-aware**: a paragraph break adds +300 ms and a chapter/section end
adds +900 ms (on top of the base and the next section's load delay). The controller derives the
boundary per unit — paragraph = the next unit came from a different block; chapter = the last
unit of the section — and passes the pause to `engine.speak(…, pauseAfterMs)`, so both engines
reuse their existing pause-during-gap handling. Base is tunable via localStorage
`orbis-piper-pause-ms`; the extras are `PARAGRAPH_EXTRA_MS` / `CHAPTER_EXTRA_MS`.

**Read ahead** (Settings → Listening: Sentence (default) / A few sentences) sets the chunk size. **Sentence** starts
soonest, and its highlight is exact: each clip is one sentence, so the highlight changes when the audio does. **A few
sentences** groups a paragraph's sentences up to `MAX_PIECE_CHARS`, the most one ORT run is given, so each chunk is
prepared in one pass and its sentences flow into each other — the choice for a device too slow to keep a sentence
ahead. Inside a multi-sentence clip the highlight is placed by character proportion (`onSpeechProgress`), which drifts
with the voice's uneven pace, so the cap also bounds the drift. Not "Passage", which Orbis already uses for a
selection in the book. There is no whole-paragraph choice: a paragraph as one clip lengthens the wait before it plays
and the drift of its highlight, and gains nothing a group of sentences lacks. A stored `paragraph` reads as **A few
sentences** (`coerceSettingValue`).

**Asking for a prepared clip marks it used** (`ClipCache.touch`, `clip-cache.ts`). Prefetch asks for the current clip
and three ahead each time one starts. Were asking to leave a clip's place in the 8-clip cache unchanged, a clip
prepared well ahead would be the oldest by its turn, and preparing the one three ahead would evict it — the clip about
to play, prepared again behind the two after it, a silence as long as all three syntheses. The debug log names any
clip missing at its turn (`cache miss at play`).

**No ORT run is longer than `MAX_PIECE_CHARS` (400).** One run's memory grows with its input, and WebAssembly memory
never shrinks, so the largest run is what counts: on an iPhone, one run of a long paragraph is enough for iOS to end
the page. The limit sits well under the longest run an iPhone handles. A sentence can be longer than any chunk limit,
so the worker cuts a text over the limit into sentences (`splitForSynthesis`, `synth-pieces.ts`), synthesizes them in
turn and joins the audio. Between two sentences goes the pause the engines put between clips — the device's base,
jittered afresh at every join (`jitteredPauseMs`; the worker is handed the base, which it cannot read) — so a joined
clip cadences like the same sentences played one by one. A sentence over the limit is cut at its clauses, and a clause
over it at its words, with no pause. Below the limit a text is one run. The `synth` debug line reports the pieces and
the largest one's phonemes.

## Listening ergonomics

- **Keep screen awake** (Settings → Listening, opt-in, default off) — holds a screen wake lock
  (`navigator.wakeLock`) while audio is playing, and Pocket mode holds it while locked whatever the setting says
  (`wantsScreenOn`); releases on pause/stop, re-acquires on
  return to foreground. Feature-detected: desktop (Electron), Android, iOS/iPadOS 16.4+.
  Because the screen staying on keeps Orbis foregrounded, this is also the practical way to keep
  audio alive on mobile (see OS controls below).
- **Pocket mode** (`tts/pocket-lock.ts`) — the full player's controls locked. On a phone or tablet the open padlock at
  the player's top right turns it on in one tap, mirroring the collapse chevron (below the ✕ in focus mode); the
  **Lock listening controls** command does it from the listening bar or either player, on any platform. Locked, the
  screen is always the full player in focus mode: `lockPocket` opens what is not open and records what it opened,
  and unlocking — the slide or the command — puts it back (`unlockPocket`): focus mode off again, the text with the
  bar. Neither starts nor stops the audio. While locked it holds the screen on, playing or paused, since a phone's
  audio stops with the screen. The player stays a read-only now-playing view; controls are hidden and the
  scrubber frozen; a lock rests at the bottom of a right-edge rail and you **slide it up** to unlock (up, not down, to
  dodge Android's swipe-down palette gesture). The reader colors are blacked out to the dark theme's `#000/#fff`
  (transient, for OLED), and the focus-exit ✕ + progress chip are hidden and exiting focus mode is blocked, so the
  drag is the only way out.
- **OS media controls (Media Session, `tts/media-session.ts`).** On **desktop** a Now Playing card shows metadata +
  working transport (a hidden, near-silent keepalive `<audio>` element gives the OS a real media
  element so the play/pause button reflects state — a pure Web Audio graph can't). **Disabled on
  iOS** (its WKWebView suspends our audio on lock, and a lock-screen play races the play
  loop). **Android shows no system controls** (its WebView doesn't bridge `MediaSession`
  to a native `MediaSessionService`).

> **Mobile background audio is not achievable from a plugin.** On iOS, WKWebView suspends the
> `AudioContext` in the background and Apple gates the fix behind a browser-only entitlement.
> It does so silently, so the player pauses itself when the page is hidden on iOS
> (`onVisibilityChange` → `pauseIfPlaying`): the position is kept and the button shows Play
> on return, rather than Pause over silence.
> On Android, background playback already works but the OS controls need a native bridge the
> WebView shell doesn't provide. A native/hybrid app (Obsidian mobile is Capacitor) with a
> native audio path would be the only real route. Wake lock is the accepted stopgap.

## Position sync

- **Highlight + page-follow.** The reading highlight is drawn and `scrollToAnchor` pages to it,
  re-applied on `create-overlay` so it survives overlay rebuilds. An **epoch** counter guards
  async continuations so stop/skip/section-change invalidate stale loops. Section advances go
  through `goToSectionStart` + the view's load hook, with a load-timeout guard.
- **Sync range vs drawn range.** `highlight(sentence)` keeps these apart deliberately.
  `currentReadingRange` is always the **sentence** — it is the page-follow target, the saved
  listening location, the resume-exact probe, and the bookmark/note/highlight target — while
  `drawnRange` (+ `drawnUnderlayRange`) is only what's painted, and exists so an overlay rebuild
  can repaint the same thing. That split is what lets paragraph mode highlight a whole block yet
  still page along sentence by sentence, and word mode paint one word without every word
  triggering a page turn.

### Reading-highlight granularity (Settings → Listening: **Highlight while reading**)

`readingHighlight` = `off` | `word` | `sentence` (default) | `paragraph`. The mode is read live, so
a change repaints the sentence being read (`applyHighlightMode`, via the view's
`applyPluginSettings`) instead of waiting for the next sentence. Independent of **Read ahead** —
how much is *synthesized* at once and how much is *highlighted* are separate choices.

| Mode | Painted | Notes |
| --- | --- | --- |
| `off` | nothing | Page-follow, saved listening location and bookmark/note targets all still work — invisible, not inert. |
| `word` | current word over a pale sentence underlay | Two overlay keys; the underlay keeps the eye's place between word steps. |
| `sentence` | the sentence | The default. |
| `paragraph` | the enclosing block | From `unit.block` (live) or `enclosingBlockRange` (recorded). |

Two details worth keeping:

- **Paragraph mode does not repaint per sentence.** `repaint` short-circuits when the block still
  `sameSpan`s what's drawn, so the highlight doesn't blink off and on at every sentence inside a
  paragraph — but it *also* requires `drawnRange.startContainer.isConnected`, because after a
  re-render the span still compares equal while its nodes are detached, and skipping the repaint
  would silently lose the highlight (`refreshRecordedHighlight`'s case).
- **Word accuracy is engine-dependent.** Web Speech reports a real char index, so word tracking is
  exact. Piper reports elapsed time over the real audio duration (120 ms ticks) and recorded MP3
  reports real per-segment `start`/`dur`, so within a sentence the word position is interpolated by
  character count — it can lead or lag slightly and resyncs at every sentence boundary. Exact
  tracking there would need word timestamps Piper doesn't emit (see Backlog).

`Overlayer.add(key, …)` self-replaces per key and appends, so stepping a word is a single overlay
swap that stays above the underlay, and foliate's `redraw()` restores both keys on resize.
- **Navigation follows the book.** When the user navigates (bookmark, search hit, Go To, TOC)
  while the bar is open, the player re-seats to that spot — the precise target sentence
  (`seekToCfi`) for bookmark/highlight/note/search/Go-To vs the page-top sentence for coarse
  jumps.
- **Survive displacement.** Opening Search / Go To / Display / Settings **suspends** audio
  (pause + hide, keeping the engine and exact position) rather than tearing it down; a layout
  re-render captures a CFI anchor and re-seats after; a "Listening paused" toast fires when the
  transport goes off-screen. Reopening resumes exactly where it left off.

## Speaking a selection, and the pronunciation glossary

Two features that share machinery: reading a selection aloud, and teaching a voice how to say a word.

### Speak (`src/reader/tts/speak-once.ts`)

Select text → **Look up** → **Speak** reads the selection in the device's live voice. Narration is
paused first and deliberately left paused: a momentary interruption shouldn't decide when reading
resumes. The button toggles to Stop while speaking (a selection can be long and there is otherwise no
way to silence it), and closing the popup stops it, so audio is never left running without its
control.

Built on the voice-**preview** functions, not on `TtsController`'s engine: `previewOrbisVoice` spins
up a throwaway Piper worker, so speaking a selection cannot disturb the reading engine's warmed
worker, its synth cache, or the playback state machine (epochs, units, highlight). `SpeakVoice`
covers all three sources — Orbis/Piper, system, and an OpenAI-compatible server — so the same helper
serves the glossary previews below.

`prepareSpeechText()` conditions the text in three steps, each preventing a real failure:

1. `clampSpeechText` caps at 1200 chars on a word boundary. Piper synthesizes the whole string before
   any audio plays, so an unbounded selection looks like a hang. The word boundary wins even when it
   discards a lot — a short correct fragment beats a mangled token espeak would read as gibberish —
   with a hard cut only for a single unbroken token.
2. `normalizeForSpeech` — the same normalization the reading loop applies, so Speak sounds like the
   narration. Without it "Chapter I" would be spoken as "Chapter Eye" here while narration says "Chapter 1".
3. `asCompleteUtterance` appends a full stop when there is none. **Piper/VITS clips very short inputs
   that aren't sentence-shaped**: a bare "doctor" can come back as just its first phoneme, worst on
   multi-speaker models (LibriTTS). The worker's `SHORT_INPUT_PHONEMES` guard zeroes duration noise
   for this class of problem but isn't enough for one word — espeak also needs the sentence boundary.
   Dangling commas/colons/dashes are replaced rather than stacked, since ",." reads as a pause.

### The glossary: matching (`src/reader/tts/pronunciations.ts`)

A `Pronunciation` is `{ word, say, enabled }`. `compilePronouncer()` builds **one precompiled
alternation**, not a `replace()` per entry. Beyond being a single scan, that's what makes substitution
**non-cascading**: sequential passes would let one entry's *output* be rewritten by another (respell
"Dover" as "doe ver", then an entry for "ver" corrupts it). Alternatives are sorted longest-first so
overlapping keys prefer the longer match.

Boundaries use Unicode lookarounds rather than `\b`, which is ASCII-only and mis-fires around
accented letters (Saëns). A capture group stands in for a lookbehind, unsupported on older iOS
WebViews. Possessives fall out correctly: an apostrophe isn't a letter, so `Tester's` matches and
keeps its `'s`.

Keys are **whole tokens with no whitespace**; internal hyphens/apostrophes and a trailing period are
allowed, so `St.`, `Saint-Saëns` and `O'Brien` are each one entry. Rejecting whitespace is what keeps
matching unambiguous — a phrase would invite overlapping matches with no principled precedence.
Replacements *may* contain spaces, because that's how you respell.

Respellings are canonicalized to **lowercase** at every ingress and inside `compilePronouncer`.
Uppercase actively fights the engine: espeak spells short all-caps runs out letter by letter, and
`normalizeForSpeech` deliberately leaves runs of ≤3 alone because those are usually acronyms it
*should* spell out (FBI). So `WUS-TUH-shur` would come back as "W-U-S, T-U-H". Two reasonable rules
colliding; lowercasing costs nothing, since stress can't be conveyed through capitals anyway.

**Out of scope by construction:** context-dependent homographs ("read", "lead"). There's no signal
here to disambiguate them, so a respelling would be wrong half the time. Said plainly in the manager.

### Where a respelling is applied

Inside `normalizeForSpeech(text, pronouncer?)`, which **every** synthesis path funnels through — live
Piper, system voices, and both recording engines — so one entry fixes all of them. Substitution runs
**last**, after the Roman-numeral and all-caps rules, so the replacement reaches the engine verbatim
rather than being re-processed (an entry whose replacement is "chapter iv" must not become
"chapter 4").

The compiled pronouncer is cached **on the plugin** and invalidated in `saveSettings()` — the single
funnel every settings mutation already goes through, so a new write path can't forget. Anything
narrower fails: `refreshViews()`, say, is called by the settings tab and not by the lookup editor,
so a respelling saved while reading would do nothing until Obsidian was reloaded (worst with an
empty glossary, which compiles to `null` and then sticks). Writes additionally call `refreshViews()`
to drop each reader's engine, since clips already synthesized would keep the old pronunciation.

Substitution is a text rewrite and never moves ranges, so highlighting is unaffected — but a
length-changing respelling does slightly widen the char-proportional position estimate's drift within
an affected sentence, which resyncs at the next sentence boundary.

### Editing and previewing (`pronunciation-editor.ts`)

The **form** is separate from its **surface**, because Orbis has two popup systems that don't mix:
`createOrbisPopup` attaches to `document.body`, which lands *outside* an Obsidian Modal's DOM, where
Obsidian's focus containment makes the input impossible to type into at all. So the reader uses a
floating popup and anything inside the Settings modal uses an Obsidian Modal (as `StyleNameModal`
does), both rendering `renderPronunciationForm`. Worth knowing before adding the next dialog.

Previews are offered per **text frontend**, not per speaker or per selected recording method. A
respelling steers letter-to-sound rules, and those live in the frontend: Piper phonemizes through
espeak-ng, a server voice runs its own G2P, a system voice uses the OS's. So two Piper speakers add a
button without adding information, while Piper vs Kokoro genuinely disagree. Selection follows which
engines are **enabled**, and skips a Piper recording voice when the live voice is already Piper.

> Deliberately **not** `readGenConfig().method`: that means "the method last recorded with", is
> device-local and unsynced, so a device that has never recorded reports `piper` and would offer a
> Piper voice despite an active, configured Kokoro server.

Previews speak inside a carrier sentence, `I will say <spelling> now.`, so the word gets mid-prose
prosody instead of the sentence-final pitch and lengthening a one-word utterance always has. They
speak the typed text **verbatim** (no dictionary) — running it back through would be circular.

Two alternatives stay out:

- **Previewing the book's real sentence.** More faithful for that sentence, but the entry applies
  everywhere, so it's optimizing for n=1 — and it grants *more* confidence, not less. A fixed neutral
  frame also makes two candidate spellings comparable to each other.
- **Per-engine respellings** (a separate spelling for the server). Held until multi-voice preview
  proves no common spelling works; the modeling cost is real and may never be needed.

### Storage: `data.json`, and sync carries it

The glossary lives in plugin settings, not in a vault file of its own. Multi-device sync publishes each entry as a record like any
other synced item, so the glossary travels without a mechanism of its own — see
[Multi-device sync](multi-device-sync.md) §Sync owns the glossary.

Two consequences worth keeping in mind here:

- **An entry has an id** (`Pronunciation.id`), minted once, and the merge is by id rather than by word. A word is a
  thing a reader retypes, and it can contain characters a file name cannot.
- **A word may appear once**, enforced after every merge rather than by the editor alone: two devices can each add
  the same word while apart, and two entries for one word means `compilePronouncer` picks by array order, which the
  two devices need not agree about.

Editing the glossary on two devices between syncs produces no conflict file to resolve by hand. Per entry,
both edits survive unless they are to the same entry, and then the later one wins.

## Recording pipeline (`src/reader/tts/recording.ts`)

**Why:** offline, higher-quality listening from cached audio — no network or cost at playback —
and quality on Android beyond what live Piper-medium gives.

Recording walks a section via `createDocument()` → `getReadingUnits()` → synthesizes
each sentence — either **on-device Piper** (`createPiperGenerator`, any tier incl. high, on its
own Web Worker so it can run *while* live playback uses a second Piper worker) or an
OpenAI-compatible `/v1/audio/speech` server (local **Kokoro** by default) via `requestUrl` —
concatenates the PCM, encodes one **MP3 per chapter** (lazy-loaded `lamejs`), and writes a
per-edition `manifest.json` recording each sentence's `cfi`/`start`/`dur` for sentence-level sync.
Runs in the background, resumable/cancellable, with a floating recording chip and an auto-opening
success panel; the **Manage recordings** dialog (`RecordingsModal`) drives scope
(book/chapters), edition/mix management, and per-chapter preview/delete.

### A chapter is a contents entry, not a spine file

**Every surface counts the same chapters.** `src/book-chapters.ts` builds the book's chapter list once — walk the
SPINE, and let each section contribute the contents entries that land in it, or contribute *itself* when the
contents mention it nowhere (a cover, a title page). That is the rule `collectByTocAnchors` already used on the
export side, and it leaves an ordinary book with exactly one chapter per section.

It matters on a book that keeps many contents entries inside a few files, such as a book of daily readings.
Section-shaped recording would give one row and one MP3 per file, with no way to skip to an entry within one, while
the contents panel and the player's ⏮/⏭ counted every entry. `Record`, `Edit mix`, ⏮/⏭ and the contents panel all
count the same list.

| | Where |
|---|---|
| The list | `bookChapters(...)` — `{ index, sectionIndex, href, anchor, label }`, memoised per book on the view |
| Where a chapter begins | `anchorCharOffsets(doc, anchors)` in the location-index measuring pass (cached, `LOCS_CACHE_VERSION` 3) for row lengths; `unitIndexForAnchor(units, doc, anchor)` for the reading unit |
| Chapter length | `chapterWordCounts(...)` — a chapter's share of its section's words, apportioned by characters |
| One boundary rule | `chapterBoundaries(raw, total)` — used for both, so a row's "42 min" and its MP3 describe the same stretch by construction |
| Identity on disk | the chapter's ordinal: `ch0042.mp3`, `manifest.chapters[].index`, `MixChapter.index`; the `href` travels alongside so a swapped book is detectable |

`unitIndexForAnchor` exists because `selectNodeContents(el)` starts a range at `(element, 0)` — *before* the
element's first child — while a reading unit starts inside the text node. The plain last-unit-at-or-before rule
therefore answers with the paragraph **above** the heading, so both the player's landing and the MP3's first
sentence would be one unit short. One resolver, shared, so they cannot disagree.

**Older manifests are rejected, not migrated** (`MANIFEST_VERSION` 2). A version-1 manifest's `index` counts spine
sections, and there is no mapping from a section to the chapters inside it that would not have to split an MP3 it
cannot split — so the book reads as unrecorded and can be recorded again. There is no migration from the
pre-editions flat layout either.

**Live → recorded handoff happens inside a file too.** A mix reading one chapter live and the next from a recording
cannot wait for the join between two documents, because a chapter boundary can fall mid-file. So
`handOffAtChapterBoundary` checks the entry starts already computed for the section and
reaches the vault only on the sentence that actually begins a new chapter.

```jsonc
// per-edition manifest — segments[] give the read↔listen sync map
{ "version": …, "book": "…", "engine": { "kind": "piper-ondevice" | "openai-compatible",
  "model": "…", "voice": "…", "format": "mp3" }, "createdAt": …,
  "chapters": [ { "index": 0, "href": "text.xhtml#day1", "audioFile": "ch0000.mp3", "duration": 812.4,
    "segments": [ { "cfi": "epubcfi(…)", "start": 0.0, "dur": 3.2, "text": "…" } ] } ] }
```

**Recorded playback** is unified into the same player: a `RecordedAudioPlayer` plays the chapter's
cached MP3, `timeupdate` → current segment's CFI → highlight + page-follow, with read↔listen
handoff both directions and cross-chapter auto-advance. The player prefers recorded audio when the
active edition covers the current chapter and falls back to the live engine otherwise (see
`startAuto` / `loadActiveEditionChapter`). Editions, mixes, and per-chapter voice provenance are
covered in **Recordings: editions & mixes** and **Voice & source** above.

**Not built:** MP3 ID3 tags + per-book `.m3u` playlists; `say`/SAPI (desktop) and cloud
(Azure/Edge) sources; auto-generate-ahead with guards (Wi-Fi-only, storage cap, confirm-before-
cloud). **Open questions:** secret storage for cloud keys (plaintext `data.json` vs desktop
`safeStorage` + mobile fallback); the long-term role of the live Web Speech engine.

## Backlog

- **2-line reading-bookmark anchor** straddling a page boundary flashes only the on-page line
  (cosmetic).
- **Exact word-level karaoke** — the `word` highlight mode exists, but only Web Speech
  (desktop/iPad) tracks exactly; Piper and recorded MP3 interpolate within the sentence. Making
  those exact needs real word timestamps: Piper would have to export alignment from the ONNX graph
  (the duration-predictor output is never requested) or run a forced aligner, or recording
  moves to an engine that emits them (Kokoro captioned endpoint / Azure / Edge).
- **Paging-lock** — suppress manual page turns while audio plays (foliate gesture-suppression
  spike); minor.

### Open bug

- **Arrow keys intermittently stop moving the caret** in reader-side popups (the respelling editor and
  the note editor; *not* the Settings-hosted editor or the Add-mix prompt, and cleared by a reload).
  The Add-mix prompt works, so `createOrbisPopup` itself is not the cause — what the two broken cases share is
  opening in response to a **book text selection**, which makes foliate's `isKeyboardSelecting` flag a
  suspect (set on keydown in the book document, cleared on keyup; a popup stealing focus mid-press
  strands it set). The editor logs only the anomaly, reporting whether the event arrived already
  cancelled or the field had lost focus — two causes with different fixes.

### Decided against (so they don't come back as phantom todos)

- **An "Advanced" full voice picker** in the respelling editor. Two frontend-based preview buttons
  cover the real cases; mounting the whole `VoicePicker` in a popup that also has a text input and a
  keyboard is a layout risk for a rare need.
- **Per-engine respellings.** Deferred until multi-voice preview proves no common spelling works.
- **Previewing the book's real sentence** rather than a carrier phrase — optimizing for n=1; see the
  glossary section for the full argument.
- **A general portable-settings vault file.** The glossary alone is the setting with a genuinely
  multi-device write pattern; every other setting would need its own portable/device-scoped call, and
  one conflict would then affect everything at once.
